# mac 原生截图软件方案规划 (架构增强版)

> **版本说明**：本规划基于《AI 协作驱动开发指南》进行了增强，补充了架构设计、数据流向与自动化验证体系。

## 1. 技术框架与边界定义

### 1.1 核心技术栈
- **语言**：Swift 5+
- **UI 框架**：SwiftUI (主界面) + AppKit (系统级窗口控制/菜单)
- **截图核心**：ScreenCaptureKit (高性能，低延迟)
- **数据存储**：FileManager + UserDefaults

### 1.2 关键限制与权衡 (Trade-offs)
- **系统版本**：最低支持 **macOS 12.3+** (依赖 ScreenCaptureKit)。
  - *决策*：放弃旧版 macOS 支持以换取更高性能和更少代码量。
- **渲染性能**：
  - MVP 阶段：使用 SwiftUI `.drawingGroup()` 进行标注绘制。
  - 优化阶段：若出现卡顿，下沉至 CoreGraphics 或 Metal。
- **沙盒机制**：
  - 必须申请 `Screen Recording` 权限 (TCC)。
  - 文件保存需处理沙盒外写入权限 (使用 `NSSavePanel` 或 `Security Scoped Bookmarks`)。

## 2. 系统架构设计 (Architecture)

### 2.1 目录结构契约
```text
MyScreenShots/
├── App/
│   ├── MyApp.swift             # App 入口
│   └── AppDelegate.swift       # 处理菜单栏、Dock、生命周期
├── Core/                       # 纯业务逻辑 (无 UI，便于测试)
│   ├── Capture/                # 截图引擎 (ScreenCaptureKit 封装)
│   ├── Storage/                # 文件保存与命名策略
│   └── Hotkey/                 # 全局快捷键监听
├── Features/                   # 功能模块 (UI + ViewModel)
│   ├── Overlay/                # 全屏遮罩、选区交互
│   ├── Editor/                 # 标注画板、工具栏
│   └── Settings/               # 设置面板
├── Shared/                     # 通用工具 (Utils, Extensions)
└── Tests/                      # 自动化测试
```

### 2.2 核心数据流 (Data Flow)
1.  **触发 (Trigger)**：快捷键 / 菜单栏点击 -> `HotkeyService`
2.  **捕获 (Capture)**：`CaptureService` 调用 `SCStream` -> 获取 `CVPixelBuffer` / `CGImage`
3.  **编辑 (Edit)**：图片传入 `EditorViewModel` -> 用户在 Overlay 层绘制 -> 生成标注图层
4.  **合成 (Compose)**：原始图 + 标注图层 -> 合成最终 `NSImage`
5.  **输出 (Output)**：`ExportService` -> 写入磁盘 / 写入 `NSPasteboard`

### 2.3 状态机模型 (State Machine)
应用应由明确的状态驱动，避免 UI 逻辑混乱：
- **Idle**: 后台静默运行，监听快捷键。
- **Selecting**: 快捷键触发，显示全屏遮罩，等待用户框选。
- **Capturing**: 用户完成框选，正在捕获屏幕像素。
- **Editing**: 捕获完成，显示标注工具栏，等待用户编辑。
- **Processing**: 正在保存或复制。

### 2.4 截图可重复触发与单实例策略
- **目标**：截图流程可被重复触发（快捷键/菜单），同时确保只有一个 Overlay 实例存在，避免多窗口堆叠与资源泄漏。
- **策略**：
  - **Overlay 复用**：全局持有 Overlay 控制器实例，触发时复用同一实例并重置状态。
  - **幂等触发**：在已进入截图流程时再次触发，优先执行“重置并重新展示”，保证用户意图可达。
  - **退出清理**：无论完成或取消，必须统一关闭 Overlay 并释放临时资源（预览图、拖拽状态）。
  - **避免并行捕获**：截图核心服务需支持重复调用但避免并行流，确保每次操作完整结束。

## 3. 验证驱动体系 (Verification Strategy)

在编写业务代码前，优先确保核心逻辑可验证。

### 3.1 自动化测试分层
- **L1: 逻辑单元测试 (Logic Unit Tests)**
  - `NamingStrategyTests`: 验证文件名生成规则 (e.g., "Screen Shot 2024-02-07 at 10.00.00.png")。
  - `HotkeyValidator`: 验证快捷键注册是否冲突。
  - `StorageTests`: 验证文件写入权限和路径拼接。
- **L2: 资源泄漏测试 (Memory Tests)**
  - 使用 Instruments 验证连续截图 50 次后，`CVPixelBuffer` 是否被完全释放。

### 3.2 验收标准 (Acceptance Criteria)
- [ ] **权限**：首次启动正确弹出屏幕录制权限提示，拒绝后有引导。
- [ ] **多屏**：支持多显示器，能在鼠标所在屏幕正确触发。
- [ ] **高分屏**：Retina 屏幕截图分辨率正确 (2x/3x)，无模糊。
- [ ] **色彩**：P3 广色域屏幕截图色彩不丢失 (Color Profile 管理)。

### 4.1 系统原生 OCR 方案 (Vision)

**目标**：在不引入额外模型包体的前提下，提供截图文本识别能力，并保证离线可用与隐私安全。

**关键决策**：
- **默认方案**：系统原生 Vision OCR，本地执行。
- **适用场景**：截图 OCR、选区文字提取、复制文本。
- **限制**：依赖 macOS 版本与系统模型质量，复杂排版需后处理优化。

**数据流 (OCR)**：
1. `CaptureService` 生成 `CGImage` / `CIImage`
2. `OCRService` 触发 `VNRecognizeTextRequest`
3. `OCRPostProcessor` 进行排序、合并、清理
4. `ExportService` 输出文本（复制/保存）

**模块接口建议**：
```swift
protocol OCRService {
    func recognizeText(from image: CGImage, completion: @escaping (Result<OCRResult, OCRError>) -> Void)
}

struct OCRResult {
    let text: String
    let blocks: [OCRTextBlock]
}

struct OCRTextBlock {
    let text: String
    let boundingBox: CGRect
    let confidence: Float
}
```

**后处理策略**：
- 按 `boundingBox` 从上到下、从左到右排序
- 合并相邻同一行文本，减少断行
- 清理换行与多余空格，输出可直接复制的文本

## 7. FAQ
Q：为什么复制/保存后没有弹窗提示？
A：为避免打断操作体验，成功只播放提示音；失败仍保留弹窗提示。

Q：成功提示音与 UI 提示的策略是什么？
A：成功场景仅提示音，不弹窗；失败场景保留弹窗与错误信息。

## 8. 马赛克功能记录 (问题特别标注)
**目标效果**：
- 预览与导出一致，覆盖区域显示清晰块状像素
- 遮挡内容不可见，不透出原图细节

**已遇到问题 (需重点关注)**：
- 预览阶段显示异常：出现全白或块状位置偏移
- 导出阶段效果不一致：与预览块大小/位置不匹配
- 内存上涨明显：预览使用全分辨率截图导致内存偏高

**规避策略**：
- 统一坐标系与缩放规则，明确点坐标与像素坐标转换
- 预览截图做下采样，避免高分屏导致内存飙升
- 马赛克块大小与导出像素化参数保持一致

## 9. 关键技术难点突破 (Key Technical Breakthroughs)

### 9.1 内存管理与生命周期 (Memory Lifecycle)
- **问题**: 截图常驻导致内存只增不减，OCR 模型加载导致峰值过高。
- **策略**: 
  - **即用即弃 (Use-and-Dispose)**: `OverlayWindowController` 仅在截图期间存活，关闭即销毁 (Set to nil)。
  - **Autoreleasepool**: 在 `CaptureService` 的 buffer 处理和 OCR 请求中包裹自动释放池，削峰填谷。
  - **CIContext 复用**: 禁用 `cacheIntermediates` 并复用实例，减少上下文创建开销。
- **Trade-off 分析 (重建 vs 复用)**:
  - **质疑**: 频繁重建是否导致 CPU 浪费？
  - **分析**: macOS 创建透明窗口的开销 (<10ms) 远小于 ScreenCaptureKit 捕获全屏的开销 (>50ms)。
  - **结论**: 瓶颈在于截图本身而非 UI 创建。选择“重建”策略可以彻底杜绝状态残留（State Residue）和内存泄漏（Memory Leak），用微不足道的 CPU 周期换取绝对的内存安全和逻辑简单性。

### 9.2 视网膜分辨率一致性 (Retina Resolution)
- **问题**: `NSImage` 与 `CGContext` 混用时容易使用逻辑点 (Points) 创建画布，导致 2x/3x 图被压缩。
- **原则**: 
  - 图片处理管线 (Crop/RoundCorner) 必须全程使用 **物理像素 (Pixels)**。
  - 仅在最终生成 `NSImage` 时指定 `size` 为逻辑点大小，以保证 DPI 元数据正确。

### 9.3 菜单与瞬态窗口捕获 (Transient UI Capture)
- **问题**: 用户点击菜单栏展开菜单后，唤醒截图会导致菜单消失 (Dismissal on Focus Change)。
- **技术难点**: 
  - **焦点抢占**: 截图 Overlay 需要成为 Key Window 才能响应快捷键和鼠标选区，但这会触发 `NSApplicationDidResignActive` 或窗口层级变更，导致 macOS 自动关闭瞬态菜单。
  - **事件传递**: 若不激活窗口，无法可靠拦截全屏鼠标拖拽事件；若激活窗口，菜单即关闭。
- **尝试方案**:
  - *方案 A*: `orderFront(nil)` 不激活窗口 -> 失败，无法建立有效 Key Loop 响应 `Esc` 等按键，且点击操作仍可能透传或关闭菜单。
  - *方案 B*: 延迟激活 (Deferred Activation) -> 失败，一旦用户开始交互（点击框选），焦点切换不可避免。
- **当前结论**: 
  - 这是一个 macOS 系统级的窗口管理行为 (Window Manager Behavior)。
  - **暂缓解决**: 建议通过“延迟截图”功能（用户设置 3 秒后截图，期间手动打开菜单）来规避，而非在交互层面强行攻克。
