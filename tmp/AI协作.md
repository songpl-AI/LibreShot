# AI 协作驱动的陌生领域开发指南：从入门到掌控

> **核心目标**：在不精通具体编程细节的情况下，通过掌握**第一性原理**、**架构全貌**和**验证标准**，实现对陌生领域开发的绝对掌控。

---

## 一、 核心理念：从“黑盒”到“白盒”

在陌生领域开发中，最危险的模式是“直接让 AI 写代码”。这会导致代码成为不可维护的“黑盒”。
本指南提倡**“认知先行，验证驱动”**的开发模式：

1.  **认知先行**：在写第一行代码前，必须先获取该领域的地图（协议、标准、架构）。
2.  **验证驱动**：先定义“怎么测”，再定义“怎么做”。验证脚本是人类手中的“尺子”。
3.  **架构掌控**：只关注模块间的接口与流向，细节实现交给 AI 填充。

---

## 二、 标准作业程序 (SOP)

### 第一阶段：认知构建与去魅 (Cognitive Mapping)
**目标**：掌握第一性原理，理解“是什么”和“为什么”。

*   **行动**：不要直接提需求，而是先让 AI 当“老师”。
*   **关键动作**：运行 [全能认知 Prompt](#工具-a-全能认知-prompt-模板)。
*   **产出物**：
    *   核心概念与官方协议（如：LSP, JSON-RPC）。
    *   行业最佳实践架构图。
    *   技术选型对比（Trade-offs）。

### 第二阶段：架构评审与权威校验 (Architecture Review)
**目标**：确保方向正确，排除 AI 幻觉。

*   **行动**：人类介入，基于 AI 提供的关键词进行校验。
*   **校验清单**：
    *   [ ] **协议确认**：AI 说的标准协议是否存在？（查阅官方 Spec）
    *   [ ] **库的活跃度**：推荐的库还在维护吗？（查 GitHub Commit/Stars）
    *   [ ] **架构合理性**：是否存在单点故障？是否过度设计？
*   **决策**：确定 MVP（最小可行性产品）的边界。

### 第三阶段：验证体系设计 (Verification Design)
**目标**：构建“掌控力”的核心环节。**在 AI 写业务代码前，先让它写验证代码。**

*   **四层验证模型**：
    1.  **协议合规性验证 (Protocol Level)**：
        *   *标准*：输入是否符合 RFC/Spec 定义？
        *   *手段*：Mock 数据包测试，Schema 校验。
    2.  **核心功能验证 (Feature Level)**：
        *   *标准*：输入 A，是否必然输出 B？
        *   *手段*：单元测试 (Unit Tests)。
    3.  **场景化业务验证 (Scenario Level)**：
        *   *标准*：在真实工作流中是否顺畅？
        *   *手段*：集成测试 (Integration Tests)，End-to-End 脚本。
    4.  **性能与稳定性验证 (Stability Level)**：
        *   *标准*：长时运行会崩吗？高并发会挂吗？
        *   *手段*：压力测试，内存泄漏检测。

### 第四阶段：增量开发与验收 (Incremental Development)
**目标**：将黑盒变白盒，分块吃下。

*   **步骤 1：骨架开发**。只写空函数和接口定义，跑通“Hello World”级的链路。
*   **步骤 2：核心填空**。实现最关键的 20% 代码。
*   **步骤 3：验证脚本回归**。运行第三阶段准备的测试脚本。
*   **步骤 4：细节完善**。处理错误、日志、配置。

## 三、 输出契约 (Output Contract)

在任何任务开始前，必须先定义“交付物清单”和“验收标准”。这是一份明确的输出契约，用来防止产出偏离预期。

**交付物清单模板**

- 目标边界：必须做与明确不做的内容
- 目录结构：新增或修改的路径
- 关键入口：启动点、触发点、配置入口
- 运行方式：如何加载、如何执行
- 验证步骤：最小可行验证路径

**不符合预期的常见原因**

- 需求没有被固化成“交付物清单”
- 验证标准缺失导致“完成感”与真实效果不一致
- 目录与入口约定不明确导致加载失败

**插件类任务最小交付规范**

- Manifest：版本、权限、入口声明完整
- 触发方式：action 或 content script 的触发路径清晰
- 作用域：仅对当前标签页或匹配页面生效
- 目录约定：扩展目录可直接被加载为未打包扩展
- 验证清单：安装、触发、效果三步闭环

## 四、 实战工具箱 (The Toolkit)

### 工具 A: 全能认知 Prompt 模板
*复制以下内容发送给 AI，开启一个新领域任务：*

```markdown
# Role
你是一个精通 [目标领域，如：LSP 语言服务/分布式系统] 的资深架构师和教育家。

# Task
我想开发一个 [简述你的目标]，但我对该领域不熟悉。请不要直接写代码，而是先按以下结构为我构建认知框架：

## 1. 领域第一性原理
- **核心概念**：用通俗语言解释该领域最核心的 3 个概念（附英文术语）。
- **底层协议/标准**：该领域依赖什么官方协议（RFC/Spec）？这是通信的基石。
- **核心权衡**：行业内通常面临哪些 Trade-offs？（如：性能 vs 易用性）

## 2. 最佳实践架构
- 请提供一个符合行业标准的“分层架构图”描述（Text-based Diagram）。
- **数据流向**：请求是如何从输入端流向处理端再返回的？
- **关键模块**：我们需要实现哪几个核心模块？每个模块的职责是什么？

## 3. 技术选型与避坑
- **推荐库/工具**：Python/TS 下最成熟的库是什么？（附 GitHub 活跃度评估）
- **避坑指南**：新手最容易犯的 3 个架构错误是什么？

## 4. 验证驱动计划
- 如果要验证这个系统是否工作，我们需要设计哪几层测试？
- 请给出一个 MVP（最小可行性产品）的开发路线图。
```

### 工具 B: 架构掌控检查表 (Architecture Checklist)
*在 AI 给出方案后，问自己或问 AI 以下问题：*

*   **解耦性**：如果未来我想换掉核心算法库，需要重写整个项目吗？（好的架构应该只需改适配层）
*   **可观测性**：如果系统出 Bug 了，我能通过日志一眼看出是哪一层的问题吗？
*   **标准兼容性**：我的实现是“私有方言”还是“标准通用”的？

### 工具 C: 验证验收单 (Verification Checklist)
*每次代码交付前，必须通过：*

- [ ] **静态检查**：Linter 无报错，类型定义完整。
- [ ] **协议测试**：生成的 JSON/数据包完全符合官方 Spec。
- [ ] **Happy Path**：最理想情况下的流程已跑通。
- [ ] **Edge Cases**：输入空值、乱码、超长数据时，系统未崩溃（Graceful Failure）。
- [ ] **环境隔离**：是否依赖本地特定路径？（应通过配置注入）。

---

## 五、 总结

> **掌控感的来源，不是阅读每一行代码，而是定义代码的边界和标准。**

通过这套方法论，你不再是一个“盲目的代码接收者”，而是一个“拥有明确验收标准的架构师”。AI 只是你的实现引擎，而你掌握着方向盘（Prompt）和仪表盘（验证体系）。
