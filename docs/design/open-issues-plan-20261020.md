验收：开关切换后 Dock 图标立即出现/消失且重启保持；打开保存面板后状态不回退；Dock 点击打开设置；区域截图、贴图、OCR 不受影响。

### 建议处置

## #47 原图翻译属性条

报告者 dingyanshan，2026-10-16，无评论。两条诉求：

1. 原图翻译的属性框仍独立，希望整合进现有属性条。
2. 翻译需要点属性框里的 ❌ 才能取消；希望改成再次点击“翻译”图标即取消。

### 现状核对

- 翻译控件是独立视图 `InlineImageTranslationView`，挂在属性条下方，整块高度固定 78pt（[OverlayView.swift:406](../../LibreShot/Features/Overlay/OverlayView.swift#L406)、[:392](../../LibreShot/Features/Overlay/OverlayView.swift#L392)）。
- 面板内含目标语言、原文/译文分段、重试/取消翻译、校正译文、移除 ❌（[ImageTranslationWindowController.swift:339](../../LibreShot/LibreShot/Core/OCR/ImageTranslationWindowController.swift#L339)）。
- 点击工具栏“翻译”：第一次创建会话并显示面板；已有会话时切换面板显隐，**不取消翻译**（[OverlayViewModel.swift:447](../../LibreShot/Features/Overlay/OverlayViewModel.swift#L447)）。这正好是报告者描述的行为。
- 翻译仅在 macOS 26+ 可用，低版本工具项直接禁用（[OverlayViewModel.swift:196](../../LibreShot/Features/Overlay/OverlayViewModel.swift#L196)）。

### 技术判断

- 把语言、原文/译文、重试、校正并入属性条行是可行的：属性条已支持按工具生成多行控件（[EditorToolbarView.swift:200](../../LibreShot/Editor/EditorToolbarView.swift#L200)），只需给 `propertyTool == nil && translationSource != nil` 增加一个“翻译”行。难点是属性条当前按 `propertyTool` 决定是否显示和高度（[:228](../../LibreShot/Editor/EditorToolbarView.swift#L228)），要改成“翻译会话存在时也显示”，并同步工具栏/属性条的布局高度与避让。
- “再次点击图标取消翻译”改动很小：`confirmImageTranslation` 在已有会话时改为 `clearImageTranslation()`。但要保留“仅切换面板”的入口，否则用户想改目标语言时会把已完成的翻译扔掉。建议点击图标=取消，面板内的“重试/校正”仍可用，并在设置或提示里说明。
- 风险：取消后原译文不可恢复。翻译结果重建需要重新识别 + 翻译，成本不低；建议点击图标取消前不做二次确认（报告者要的就是顺滑），但保留“重试”路径。

### 建议方案

1. 属性条新增翻译行：语言下拉、原文/译文分段、重试、校正、移除；去掉独立面板及其 78pt 预留。
2. 翻译图标改为“开/关翻译”：有会话时点击即移除翻译，回到普通属性条。
3. 翻译会话存在时属性条常显，选区变化仍按现有规则清理（`clearImageTranslation`）。
4. 保持 macOS 26+ 门槛，低版本不显示翻译项。

验收：开始翻译后属性条不跳动、不重叠；切换工具后翻译控件仍在；点击翻译图标取消翻译且工具栏恢复；重试和校正可用；保存/复制/贴图导出的是当前“原文/译文”视图；文字选区变化清理翻译。

## #48 指针小工具与画布属性

报告者 dingyanshan，2026-10-16，无评论。两点：

1. 指针已经选不中任何已有标注，选中标注时下方显示的是该标注工具的属性；指针只能选整张截图、调整体位置，显得多余。
2. 建议给指针加属性条，作为“整张截图的外边框属性”：边框颜色、粗细、圆角。

### 现状核对

- 1.3.28 已把“指针选中后仍留在指针模式”作为改动交付：`selectExistingAnnotation` 在 `selectedTool == nil` 时不再切换到标注工具（[OverlayViewModel.swift:884](../../LibreShot/Features/Overlay/OverlayViewModel.swift#L884)）。所以第 1 点的前半句（不能选中）应已在 1.3.28 缓解，需要报告者用 1.3.28 复测确认。
- 仍然成立的部分：
  - 画笔按设计不可选中（`selectExistingAnnotation` 直接 return）。
  - 选中标注后 `propertyTool` 返回标注类型（[OverlayViewModel.swift:1458](../../LibreShot/Features/Overlay/OverlayViewModel.swift#L1458)），属性条显示的是该标注的属性，**指针本身没有属性条**。
  - 画布只有全局布尔 `useRoundedCorners`（[SettingsService.swift:74](../../LibreShot/LibreShot/Core/Storage/SettingsService.swift#L74)），圆角固定 `min(16, …)`，没有边框颜色/粗细，也没有运行时入口。导出时在 `styledImage` 里做圆角裁剪（[CaptureService.swift:618](../../LibreShot/LibreShot/CaptureService.swift#L618)）。
- 属性条在没有工具、没有选中标注时高度为 0（[EditorToolbarView.swift:228](../../LibreShot/Editor/EditorToolbarView.swift#L228)），所以“指针属性条”是新增而不是修改。

### 技术判断

- 画布属性（边框颜色、粗细、圆角）本质上是对最终导出图做二次绘制，路径清晰：扩展 `styledImage` 先画边框再裁圆角，同时更新编辑态预览（`OverlayView` 目前只按圆角裁剪：[OverlayView.swift:36](../../LibreShot/Features/Overlay/OverlayView.swift#L36)）。
- 三个设计问题必须先定：
  1. **全局设置还是单次会话**：现有圆角是全局设置。建议属性条里的值作为当前会话覆盖，完成后写回全局默认，和标注样式的“记住上次”一致。
  2. **边框会不会吃掉内容**：截图没有外边距，描边若压在图像边缘会遮住 1–N 像素。建议向内描边并限制在 1–12pt，或增加可选外边距（更大改动，暂不做）。
  3. **圆角与边框的顺序**：先描边后裁剪圆角，避免四角出现直角残边。
- 预览与导出必须一致：现在编辑态只裁剪圆角、导出时才应用 `styledImage`。加边框后要两边同源，否则用户会看到“预览没有、保存有”。
- 贴图窗口也调用 `styledImage`（[PinnedImageWindowController.swift:26](../../LibreShot/Core/PinnedImageWindowController.swift#L26)），需一并验证。

### 建议方案

1. 属性条新增“画布”行：边框颜色（预设 + 取色器）、粗细 0–12、圆角 0–24；无选中标注/无工具时显示。
2. 新建 `CanvasStyle`（颜色、线宽、圆角）替代布尔值；旧 `useRoundedCorners` 迁移为“圆角 16 / 0”，默认规则不变。
3. 预览和导出共用同一绘制函数；画笔、OCR、贴图、长截图导出都走它。
4. 指针交互保持 1.3.28 行为：指针可选中并拖动矩形/椭圆/箭头/文字/序号；画笔仍不可选，但可在指针下命中时给出提示。

验收：三种边框参数在预览、复制、保存、贴图一致；0 粗细/0 圆角无描边；小选区大圆角不变形；贴图重新编辑后参数保留；旧偏好升级后表现不变；多显示器与 Retina 边缘不发虚。

### 建议处置

回复时先确认 1.3.28 是否已解决“选不中”，再说明画布属性纳入下一版；若报告者确认指针已可用，可把 #48 范围收窄为“画布边框属性”。

## #45 内存回落与“编辑图片”

报告者 dingyanshan，2026-10-16，无评论。两部分：

1. 内存：启动 16.1M → 截图后约 60M → 各种功能后峰值 220M、回落到 135M；希望回到启动水平。
2. 参考 macOS“预览”的分工，把截图与标注拆开，各自结束即退出；并给 Finder 的“打开方式”增加“编辑图片”。

### 现状核对

- 内存策略已有明确文档和验收顺序：[memory-lifecycle-policy.md](memory-lifecycle-policy.md)。其中已判定“不把固定 20–30 MiB 当保证”“外部 helper 不能释放主进程仍持有的对象”“当前 OCR 已采用子进程承载重任务”。
- 2026-10-05 维护决定取消约 10 MiB 目标，#5 已关闭；但这不等于接受“用完不回落”。
- 之前的 1.3.10 调查：25 次普通截图后闲置约 41–43 MiB，OCR/翻译批次后约 52–57 MiB；长截图采集中峰值约 190 MiB（不能当常驻值）。那是 1.3.10 的数据，1.3.28 未重测。
- 应用**不能打开图片文件**：没有 `NSOpenPanel` 图片选择、没有 `CFBundleDocumentTypes`、没有 `application(_:open:)`；`ImageEditorWindowController` 只从截图流程内部创建（[LibreShotApp.swift:579](../../LibreShot/LibreShot/LibreShotApp.swift#L579)）。
- 应用是沙盒（App Sandbox + Desktop 读写 + 用户选择读写，见 [LibreShot.entitlements](../../LibreShot/LibreShot/LibreShot.entitlements)），打开外部文件后需要 security-scoped bookmark 才能持续读写。

### 技术判断

- 内存部分不能承诺“回到启动值”：物理 footprint 的回落在 ARC 释放后还受 malloc 空洞、图形 surface、系统框架缓存影响（文档已说明）。可承诺的是：**会话结束必须主动释放原图/译图/识别区域，并给出可复现的采样曲线**。
- 报告者的 220M 峰值最可能来自：全屏原图 + 裁剪图 + 标注合成图 + 预览位图同时存活；翻译同时持有原图、译图、区域；贴图窗口持有独立 document。需要按文档第 3 步分进程采样，先证实再改。
- “编辑图片”是独立且明确的功能，和 #50 共用前置能力：从文件加载图片 → 打开编辑窗口 → 保存/复制/贴图。技术上就是 `ImageEditorWindowController(image:)` 增加一个 `URL` 入口 + 文档类型声明 + 权限 bookmark，风险低。
- Finder“打开方式”需要 `CFBundleDocumentTypes`（`LSHandlerRank = Alternate`，避免抢默认）和 `application(_:open:)`；沙盒下首次访问要 `startAccessingSecurityScopedResource`，最近文件存 bookmark。

### 建议方案

分两条线，不混在一起交付：

1. **测量线（P1 调查）**：在 1.3.28 正式包上用 `MemoryTrace` 采冷启动、单次截图、OCR、翻译、贴图、长截图完成/取消、关窗后 1/15/60 秒；主进程与 OCR worker 分开记录；重复批次看阶梯增长。有证据再定点释放，不先拆进程。
2. **功能线（P2）**：`打开图片…` 菜单 + 拖到菜单栏图标打开 + Finder“打开方式”；打开后进入现有编辑器，保存默认另存（不覆盖原文件），复制/贴图沿用现有动作。
3. 文档：把“编辑图片”写进 README/使用说明；内存结论按实测更新，不用“已优化”措辞。

验收（功能线）：PNG/JPEG/HEIC 打开正常，Retina 尺寸正确；保存默认另存且可覆盖需确认；沙盒重启后最近文件仍可读；Finder 打开方式出现 LibreShot；关闭编辑窗口后图片释放（采样对比）。

## #50 新的架构路线

报告者 dingyanshan，2026-10-18，2 条评论（10-19 补充流程，10-20 反馈 Automator+预览约 5 秒才弹出）。核心设想：

1. 用系统截图，只引导用户设置自动保存文件夹。
2. 常驻监听该文件夹，有新图片就拉起“标注程序”打开它。
3. 标注完成后关闭标注程序，内存随之回收；最好在截图原位弹出、标注后覆盖原图并复制到剪贴板、1 分钟后自动关闭。

### 现状核对

- 没有文件夹监听（无 FSEvents / `DispatchSource` / `NSMetadataQuery`），也没有“打开图片”入口，所以标注模式的两端都不存在。
- 应用本来就常驻菜单栏：`LSUIElement` 未设置，启动时 `.accessory`（[LibreShotApp.swift:77](../../LibreShot/LibreShot/LibreShotApp.swift#L77)）。监听一个文件夹的增量成本很小，不存在“再多 5–10M 常驻”的问题，但也**不因此省内存**。
- 截图会话结束已有释放逻辑（`memory-lifecycle-policy.md` 的生命周期表）；拆进程能“保证归还”，是因为进程退出，而不是因为监听。
- 沙盒：Desktop 有读写权限；其他目录需用户在 `NSOpenPanel` 里授权并持久化 bookmark。覆盖原图属于写用户文件，需同一授权。

### 逐条技术判断

| 设想 | 判断 | 说明 |
| --- | --- | --- |
| 系统截图 + 自设保存目录 | 可行，但脆弱 | 目录可用 `defaults read com.apple.screencapture location` 读取；修改后要 `killall SystemUIServer`。只能引导，不能代设 |
| 监听文件夹 | 可行 | FSEvents 或 `DispatchSource` 都行；常驻成本远低于 5–10M。需处理系统截图缩略图延迟写盘、本地化文件名（`截屏…`/`Screenshot…`）、拖入的其他图片误触发 |
| 自动拉起标注窗口 | 可行 | 但延迟 300ms 是乐观值。用户看到 5 秒主要是 Automator 文件夹动作的轮询周期 + 预览冷启动；同进程 FSEvents + 预热窗口现实值约 0.3–0.8s。可预加载隐藏窗口降低首帧 |
| 在截图原位弹出 | **不可行** | PNG 不记录截图区域，无法还原屏幕坐标。只能近似：按鼠标位置或固定位置 + 上次窗口尺寸 |
| 标注后覆盖原图 | 可行但危险 | 破坏性写用户文件；沙盒需 bookmark。建议默认“另存标注副本 + 复制到剪贴板”，覆盖作为显式选项 |
| 1 分钟后自动关闭 | 可行 | 但会打断多张连续标注；建议改为“完成后按设置延时关闭”，默认关闭该行为 |
| 省内存 | 部分成立 | 省的是标注窗口关闭后的常驻；但“预加载标注程序”又要求它常驻，二者互相抵消。真正决定回收的是进程是否退出，和截图来源无关 |

### 关键风险

1. **体验倒退**：现在是“框选→标注→完成”一个手势闭环；改成系统截图后，用户先看到系统缩略图，再等窗口弹出，属于两段式。报告者已接受延迟，但这是产品取舍，不是纯技术优化。
2. **内存目标与预加载冲突**：要快就得常驻标注进程；要省就得退出。1 分钟自动关闭是折中，但空闲峰值仍在。
3. **文件语义**：覆盖原图会丢失原始截图；自动保存 + 剪贴板 + 覆盖三者叠加容易产生“保存到哪了”的困惑。
4. **可维护性**：两条截图链路（自带遮罩 + 外部文件）要共用编辑器，等于把 `ImageEditorWindowController` 变成正式入口，属于结构改动。

### 建议方案（分阶段，不一次投入）

- **阶段 0（已完成）**：1.3.28 已让指针可选、OCR 在原图上选字，编辑器可复用性提高。
- **阶段 1（小）**：做“打开图片文件 + Finder 打开方式”（与 #45 功能线同一件事）。这是标注模式的前置，单独就有价值。
- **阶段 2（中，可选开关）**：设置里增加“监听截图文件夹”。开启后监听 → 打开编辑器；窗口位置用鼠标位置近似；默认另存标注副本并复制，覆盖作为高级选项；完成后按设置延时关闭。默认关闭，文案写明延迟与覆盖风险。
- **阶段 3（按证据）**：只有测量证明“同进程释放后 footprint 不回落”是主要矛盾，才考虑把编辑窗口拆成独立进程/helper；否则不拆。这与 `memory-lifecycle-policy.md` 的判定一致。

阶段 2 验收：开启后系统截图保存即打开，端到端延迟有实测值（目标 < 1s，记录 P50/P95）；关闭监听后恢复原流程；非截图图片不误触发；覆盖行为有明确开关；标注关闭后进程内存采样回落；权限拒绝时给出可操作提示。

### 建议处置

回复时承认方向可行，但要说明三点：原位弹出不可实现、延迟主要来自监听方式而不是图片保存、内存收益取决于进程是否退出而不是拆分本身。给出阶段 1/2 的计划，不承诺“彻底解决内存”。#50 保持开放，作为专项跟踪。
