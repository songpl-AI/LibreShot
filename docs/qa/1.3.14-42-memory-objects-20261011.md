# Build 42：长截图失败后的内存对象清单

2026-10-11，正式安装副本 1.3.14 (42)，PID 42515。本轮三次固定 120px 追加成功后，完成时因尾帧 unmatched 报错，尚未渲染长图。报错窗口已关闭；设置窗口关闭动作未取得可靠 UI 确认，因此本表不是冷启动/纯待机或成功长图后指标。普通截图后的严格关窗测量另见 [本包 QA](1.3.14-42-memory-reuse-20261011.md)。

原始证据目录为 `dist/build42-runtime/after-long-failure/`：`vmmap-before-heap.txt`、`heap-summary.txt`、`heap-zones.txt`。采集时先保存 vmmap，再运行 heap；没有在长截图流运行期间做 heap/vmmap。heap 会读取目标内存并可能改变驻留情况，后面的 heap 不能替代前面的自然状态。未开启 MallocStackLogging，未知分配仍没有分配栈。

## 主进程实际负担

11:29:18 的 physical footprint 为 **50.4 MiB**，历史 peak 为 170.4 MiB；历史 peak 没有阶段标签，不能归因某功能。同期 RSS 125456 KiB（122.5 MiB），它与 footprint 是不同指标。没有本次同时活动监视器读数，不能解释用户此前的 122MB。

下面使用互斥 vmmap 区域的 dirty+swapped 近似列出私有页归属，工具列已四舍五入，合计接近 50.4 MiB。此维度包含换出负担，不等于全部当前 RAM；更不是精确业务对象清单。

| 区域 | dirty+swapped | 是否能优化 |
| --- | ---: | --- |
| MALLOC_SMALL | 32.16 MiB | 最大调查对象。包含业务/框架对象及 allocator 空间；不能全部称为 SwiftUI，也不能承诺全部可释放 |
| 框架/运行时 `__DATA`、`__DATA_DIRTY` | 5.25 MiB | 常驻状态，通常通过减少初始化间接优化；不能直接清空 |
| CoreAnimation | 1.72 MiB | 可缩短窗口/图层持有时间，系统回收时机不完全由应用控制 |
| malloc metadata | 1.27 MiB | 通过减少对象/arena 数量间接优化 |
| shared memory | 1.28 MiB | 来源未追到业务栈，待查 |
| 其余区域 | 约 8.72 MiB | 小堆、图形、线程、数据段等混合成本，逐项定位后才能判断 |

DefaultMallocZone 有 21.9 MiB allocated 和约 9.63 MiB dirty+swap fragmentation。后者是分配器页内空隙/开销的估计，**不是一个可直接删除的缓存**，不能直接作为未来收益承诺。MALLOC_SMALL 的 65 MiB virtual 也不能当作65 MiB实际 RAM。

## 还分配着什么

heap 分类完整解析共 3414 行，总分配 **37403293 bytes（35.67 MiB）**。下表互斥，但只有 malloc allocation bytes；**不能加到 footprint 或上一张表，也不能用来给其逐项业务归属**。

| 对象类别 | 分配容量 | 可优化性与证据边界 |
| --- | ---: | --- |
| 未识别 non-object | 20.96 MiB | 已查明其中 12.5 MiB 是20个640 KiB的 purgeable 分配；其当前 resident/dirty/swapped 均0。其余约8.46 MiB仍需分配栈，不能宣称全可回收 |
| Foundation / CoreFoundation 具名对象与存储 | 3.13 MiB | 字符串、字典、Data 等。可减少不必要副本，但没有栈不能认定哪个功能造成 |
| Swift runtime metadata | 2.90 MiB | 类型/泛型初始化成本，正常关闭窗口通常不回收；延迟初始化可能减少部分，但需等价实验 |
| ObjC 类数据、方法缓存 | 1.75 MiB | 运行时基础成本，不能按截图结束直接清掉 |
| SwiftUI / SwiftUICore / AttributeGraph 具名对象 | 1.53 MiB | 窗口/视图节点可以优化；此数不包含所有未知内部存储，不能称为SwiftUI总成本 |
| CoreGraphics / QuartzCore / Metal 等具名对象 | 0.74 MiB | 只含对象/具名存储，图像backing另在其他分类；不是图形资源总量 |
| AppKit 具名对象 | 0.55 MiB | 窗口、菜单、布局状态。可以减少重复创建/持有，必要的菜单栏功能仍有成本 |
| 本应用直接具名对象 | 约0.001 MiB | 8个直接对象合计1280 bytes，仅对象头/自身字段，不包含它们引用的框架对象或buffer |
| 其他具名或未知对象 | 4.10 MiB | CoreSVG、CoreUI、字体、Swift存储、闭包、Combine等，按栈和生命周期继续定位 |

本应用直接对象包括 SettingsService、HotkeyService、AppDelegate、CaptureService、SettingsWindowController、StreamLifecycleGate、SettingsView、SoundService，各1个。该快照没有识别出 LongCaptureSession、LongCaptureFrameAccumulator、LongCaptureStitcher、LongCaptureStreamService、OverlayViewModel 的直接实例；出现它们名字的 keypath 是运行时类型/属性缓存，不能当作会话还活着。这个观察支持结束后清理，但不是所有路径无泄漏的证明。

DefaultPurgeableMallocZone 的12.5 MiB来源已确认到zone，其分配栈/业务来源尚未知。其驻留和换出为0，故不将它当作当前可降低footprint的12.5 MiB。之前未知大块的历史大小也不能直接替代本build分类。

## 优化优先级

1. **先修长截图正确性。** 本轮拒绝发生在已追加后的尾帧匹配；不能通过忽略错误或强行保存减少工作量，避免再次漏行。独立 footer 恢复原型仍有动态footer反例，当前不合并到生产。
2. **追踪 small heap 中的未知存储与碎片来源。** 需要独立诊断启动的分配栈，对照冷启动、设置打开/关闭、截图结束。当前应用不换包、不刷新权限，诊断开销不能当产品基线。来源清楚后才确定缓存/副本/lifecycle改法。
3. **延迟视图/运行时初始化是待测方向。** 源码已经按需创建自管设置controller并在关闭时释放，但入口仍有 SwiftUI Settings scene。本轮有存活的SettingsWindowController，不能拿这个快照证明清理路径失败或贸然重写全部UI。
4. **保留已做的图像buffer复用和owner释放。** build42独立PNG导出峰值收益已验证；它不等于完整app待机收益。本快照没有活跃大图像malloc backing，继续改图像释放不一定能降低这32.16 MiB小堆负担。

**20–30 MiB待机目标仍未达到，也没有证据承诺再降低80 MiB。** 当前已有可审查的对象/区域列表，但未知业务栈和allocator页归属尚未闭合，不编造每个功能的精确占用。
