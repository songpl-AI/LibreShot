# 贴图定位、快捷键与滚轮缩放评估

日期：2026-10-11。本轮评估当前工作区代码，只新增此记录，不实现贴图修改、不构建安装包、不修改用户偏好。工作区已有马赛克首次预览对齐修复，本评估不改变其内容。

## 1. 截图位置到居中贴图

### 已确认原因

- `LibreShotApp.performAreaCapture` 已将选区从屏幕内左上角坐标转换为 AppKit 全局坐标 `globalRect`，并用于裁剪。
- 随后仅传图像与动作给 `handleImageAction`；`.pin` 分支只传图像给 `PinnedImageWindowController`，原选区位置和目标显示器丢失。
- `PinnedImageWindowController.initialWindowFrame` 明确以 `NSScreen.main.visibleFrame` 为依据居中；不是动画误差，也不是截图过程中选区算错。
- `fittedWindowSize` 同时设置约 360×280 的最小初始窗口，并在大图时缩至可见屏幕的 80%。图片在窗口内 aspect-fit，小截图可能放大或带空白，即使只改窗口原点也不能保证与原截图重合。
- 普通贴图和长截图预览共用这些逻辑，不能整体取消长截图预览的适屏行为。

### 推荐方案

1. 区域截图沿结果路径传递可选的截图位置上下文：已经计算好的全局选区矩形及目标显示器 ID；不在窗口关闭后重新读取鼠标或 `NSScreen.main`。
2. 普通区域贴图创建前就设置原选区位置和逻辑点尺寸，首次显示不经过居中／移动动画；按截图时的逻辑大小显示，而不是按 Retina 原始像素数放大。
3. 普通贴图取消固定 360×280 的初始下限，不强制缩至可见区域的 80%；按源选区显示，避免小图出现大空白或放大。截图位置在菜单栏／Dock 附近时不常规强制移入 `visibleFrame`，否则仍会产生跳动。
4. 长截图预览保留现有适屏居中策略。全屏截图、长图编辑器或其他没有唯一源区域的入口单独定义回退：优先当前文档所在屏幕，适屏展示；不虚构原截图位置。全屏源位置如需要恢复，应从捕获时保留，不能从编辑窗口位置反推。
5. 目标屏幕断开或原矩形完全不可达时，再回退到可用屏幕并保证可拖动／关闭。

影响：中等，涉及结果路径与贴图初始化，但不需要修改截图采集或图像标注算法。验收重点：普通小图／大图原位置与尺寸、Retina、多屏负坐标、目标屏幕变化、长截图预览回退、连续贴图。

## 2. 快捷键贴图

### 已确认现状

- 设置的“工具栏”页对每个动作（包括 `.pin`）提供快捷键录制。
- `SettingsService.setEditorShortcut` 已验证按键合法性，检查与全局截图／其他编辑动作的冲突，并持久化。
- `OverlayViewModel.performEditorShortcut → performToolbarItem(.pin) → confirmPin` 已完整支持当前选区贴图，`confirmPin` 包含标注和提交文字的共同出图路径。
- `EditorShortcut.defaults` 目前只有保存、另存为、完成、撤销；贴图缺少默认绑定，用户不易发现。
- 当前快捷键在文字输入时只允许保存类命令，贴图绑定不会抢占文字输入。按键重复事件不会反复生成贴图。

### 推荐方案：截图编辑中按快捷键直接贴图

建议默认 ⌘P，沿用现有本地编辑快捷键机制。新用户和主动恢复快捷键者获得默认绑定；已保存的快捷键配置保留，提供明确的设置入口提示，不能对所有“缺少 pin 字段”的用户强行补键（这也可能表示用户曾主动清除）。工具栏悬停提示已经会显示绑定，说明文案补充“框选／标注后按 ⌘P 贴图”。

此方案无需新增全局监听或权限，截图编辑还未结束时按键直接出图，与按钮行为一致。影响小，不需要新建截图流程。保持文字输入、属性输入、译文未就绪、长截图采集中的现有保护。

### 若需求指“按 Enter 完成后，再用全局快捷键贴上一张”

这是不同的功能：目前没有“最近一次截图及源位置”的专用结果缓存，也没有对应全局动作。需要新增全局绑定、冲突与注册失败提示，并为最近截图保留最终标注结果与位置；定义无截图可贴时的行为、缓存替换／退出释放和内存上限。直接读取剪贴板会受其他应用复制内容影响，也无法可靠恢复原截图位置。

影响中等，建议单独实现，不与补默认 ⌘P 混为一项。

若希望从桌面按一个全局快捷键“框选后松手立即贴图、跳过编辑”，则还需要截图会话明确携带“结束即贴图”的目的，处理取消、重复触发和常规截图共存；同样属于额外流程，不是简单补快捷键。

验收重点：默认键、用户自定义／清除／恢复、冲突、持久化、文字输入保护、键盘重复、快捷键结果与按钮一致。

## 3. 滚轮缩放贴图

### 已确认原因

贴图窗口只设置 `.resizable`，图片随窗口 aspect-fit，所以可以拖边调整。`PinnedImageView` 中 `scale`／`lastScale` 状态没有用于绘图，也没有滚轮或捏合缩放处理。不存在“滚轮方向错了”之类的现成逻辑，当前就是缺少该交互。

### 推荐方案

1. 仅普通贴图接收鼠标所在窗口的滚轮事件，局部事件处理，不使用全局事件监听；先保留长截图预览的现有行为。
2. 使用一个统一缩放值按原图比例同步调整窗口和图片，避免仅用 SwiftUI `scaleEffect` 造成裁剪、点击区域与图片范围不一致。拖边缩放仍可用，并更新滚轮缩放的当前基准，防止下一次滚动跳回旧尺寸。
3. 以鼠标指向的图像位置为缩放锚点：缩放后该点仍在原屏幕位置，不每次将窗口重新居中。边界回退只在实际不可操作时发生。
4. 鼠标滚轮采用适量分档，触控板采用小幅连续变化；限制异常大增量，处理惯性，避免停手后继续快速放大。设最小／最大缩放范围和可操作的尺寸下限，最终阈值需实机体验。
5. 右键菜单增加“恢复原始大小”；触控板捏合可复用同一套缩放逻辑。初期不必增加常驻工具栏。
6. 缩放只改变显示，复制／保存继续使用原图分辨率；拖动、透明度、双击关闭均保留。

影响：中小，主要在贴图窗口与输入处理，值得处理。验收重点：鼠标与触控板、不同滚轮粒度、惯性、缩放锚点、连续拖动／缩放、边缘与多屏、复制保存原始分辨率、长截图预览隔离。

## 本轮验证

临时工具直接编译生产窗口、设置和编辑动作代码，以独立 UserDefaults 域执行，不修改安装应用或系统授权：

`bash tests/compile-checks.sh /tmp/libreshot-pin-review/checks LibreShot/Core/PinnedImageWindowController.swift /tmp/libreshot-pin-review/PinChecks.swift`

`/tmp/libreshot-pin-review/checks`

结果：

- 100×80 图像构造的窗口中心与主屏可见区域中心重合，本机实际窗口 360×281，确认小图被较大窗口承载。
- 向真实窗口的内容视图注入滚轮事件，窗口大小不变；结合源码确认没有缩放处理。此为程序化事件验证，不声称已测试实体鼠标滚轮。
- 新设置域贴图默认快捷键为空。
- 设置 ⌘P 成功且可跨 SettingsService 实例读回；执行按键会分派 `.pin` 和当前选区；文字响应器活跃时不执行贴图。

临时源码与日志：`/tmp/libreshot-pin-review/PinChecks.swift`、`results.log`；系统可能清理。

建议顺序：先修复普通区域贴图的位置和初始尺寸，再补默认贴图键，最后在相同窗口几何基准上加入滚轮缩放。三个方案可在同一轮开发中落地，但都需要各自的回归证据和最终新包安装验收。
