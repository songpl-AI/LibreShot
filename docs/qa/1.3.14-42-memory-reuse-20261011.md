## 待机内存测量

截图编辑和设置窗口已关闭，菜单栏应用保持运行，针对 PID 42515 连续约 3 分钟采样 RSS 与 `vmmap -summary`：

- `ps` RSS 从 134064 KiB 回落并稳定在约 126224–128176 KiB（约 123–125 MiB）；这不是同一时刻活动监视器 Memory 的证据，不能直接等同。
- physical footprint：51.4 MiB → 46.6 MiB，并在后续样本稳定约 46.7 MiB。
- physical footprint peak：170.4 MiB。vmmap 只提供进程峰值，未记录阶段标记，不能把它归因于某一个截图、导出、OCR 或长截图阶段。
- 11:13 快照的 `MALLOC_SMALL` 为 virtual 59.2 MiB、resident 26.6 MiB、dirty 25.7 MiB；11:16 快照则为 virtual 58.8 MiB、resident/dirty 3.4 MiB、swapped 25.8 MiB，说明 allocator/压缩/换出状态会变化，不能把一列当作业务对象归属。`MALLOC_SMALL (empty)` 与 `MALLOC_LARGE` 均没有相应的 live resident 大块（11:16 的 `MALLOC_LARGE` 为 17.6 MiB virtual/empty、resident 0）。
- 当前样本的 CoreAnimation resident 约 416 KiB、IOSurface resident 约 128 KiB；这些数字只描述该时点。
- `__TEXT` resident 361 MiB 主要是共享框架映射，不能当作 LibreShot 私有可回收对象直接相加；vmmap 总 resident 也不能直接等同活动监视器的单一 Memory 数字。

## 本轮长截图失败与回落

用户实体触发长截图遮罩后，由桌面工具框选公开 fixture 正文区域并操作三次固定 120px 按钮。默认日志记录三次接受高度 1350→1470→1590→1710，但每次新增后约 70–96ms 又转为 unmatched；用户点击完成后确认报错，桌面工具读取到“有滚动画面未能接上，本次未生成完整长截图”。最后诊断为正反 matcher 均 `no-coarse-candidate`，横向采样后的尺寸 240×1350、变化列 11、变化行 126、范围 442–567，`stationaryRedraw=false`。

这证明三步追加后尾帧校验失败，发生于渲染/PNG 保存前；没有证据把本轮失败归因于权限、PNG 复用或内存不足。该运行未开启完整逐帧 trace，也没有保留原始输入帧，因此不能确定局部变化对象、丢帧情况或具体 stationary 拒绝分支。现有兜底对原图变化纵向要求小于 64px，与末帧变化跨度不相容；这只是解释候选，不能据此直接放宽保护条件。详细源码证据见 [本轮分析](../../dist/build42-runtime/long-01/failure-analysis.md)。

本轮另完成 11 组独立公开合成输入：同位置变化的高度由 64px 增至 65px 即从 stationary 接受变为拒绝；同位置 126px 高、74px 宽的强变化得到 `no-coarse-candidate`、范围 442–567、12 个缩采样变化列，与现场 11 列是近似而非完全相同。真实 1700px gap、低对比运动和局部重排仍被拒绝；72px 正常滚动正确匹配。探针只调用 matcher/stationary，不含最终渲染或生产原始帧，证明这类机制可导致无滚动失败，但不能识别现场变化对象；未放宽生产保护条件。证据见 `dist/build42-offline/stationary-local-change/results.json`。

RSS-only 采集区间 11:16:20–11:27:24 共 655 个样本，最高 204352 KiB（约 199.6 MiB），发生于 11:21:25；不能称为 footprint 峰值或活动监视器 Memory。错误完成后 RSS 从 157216 KiB 回落至 119184 KiB。采集脚本已通过 STOP 正常结束，其自己的日志子进程已退出。

11:29:18、报错窗口关闭后的原始 vmmap 为 footprint **50.4 MiB**，历史 peak 仍 170.4 MiB。设置窗口关闭曾尝试但桌面工具状态未能确认，故这是“长截图失败后”快照，不能称为严格纯待机或成功长图后的回落。配套 heap 总分配 37403293 bytes（35.67 MiB）；其中未知 non-object 20.96 MiB，按 zone 核对后 12.5 MiB 来自 `DefaultPurgeableMallocZone`，其 vmmap resident/dirty/swapped 均为 0，不能承诺释放这部分会减少 12.5 MiB footprint。完整分类与优化边界见 [最新内存清单](1.3.14-42-memory-objects-20261011.md)。

## 结论

build 42 的安装副本、录屏实际遮罩、重启前后普通截图和保存已取得证据；输入监控实体 Option 和 OCR 仍待验。普通区域截图并关闭设置/编辑窗口后，本轮 physical footprint 约 45.8–46.7 MiB；这不能推广到长截图、OCR 或翻译后的待机值。`ps` RSS 约 123–125 MiB，不能直接等同用户在活动监视器看到的 Memory。`MALLOC_SMALL` 是 allocator 分区，不是业务对象清单；要归因仍需 Allocations/栈证据。PNG 复用的 1500×6000 独立导出实验显示无圆角峰值下降，但本次真实 app 的 170.4 MiB peak 没有阶段归属，不能把它当成优化后的正式峰值。

长截图质量仍是独立问题：本轮真实测试失败，已有 matcher 的边缘变化误拒绝和 footer=0 缓存缺陷离线证据；本 build 没有新增长截图算法修复，因此不把普通截图验收扩展成“长截图已修复”。本次失败尾帧的正反 motion 匹配均在 footer 分支之前拒绝，不能把 footer 恢复原型当成本轮失败的修复。
