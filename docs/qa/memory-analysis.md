# 内存分析（2026-09-15）

## 范围与测量口径

最初的分析阶段只做隔离实验，没有修改生产实现，也没有清空用户剪贴板、下载语言包或替换正在运行的应用。随后按用户要求实施了剪贴板和长截图优化，结果见文末“已实施与回归”。

- 当前安装版：`/Applications/LibreShot.app`，1.2.0 (7)。9 月 14 日的 `vmmap -summary` 快照：physical footprint 91.0 MiB，历史峰值 181.7 MiB。这是使用后的快照，不是冷启动测量。
- 用户观察的冷启动 20 多 MB 尚未独立复测；不把它与下面最小测试程序的基线混用。
- 隔离程序用 `swiftc -O` 编译当前工作区实际服务代码，通过 `task_info(TASK_VM_INFO).phys_footprint` 读数。未加载完整应用的菜单、截图遮罩和窗口，不能将它的绝对内存直接当作优化后完整应用的内存。
- 图片实验使用生成的 2400×1400 RGBA 文字图、独立 UserDefaults 和命名剪贴板；没有访问用户剪贴板内容。每次操作包裹 autoreleasepool，返回后等 1 秒再采样，连续 5 次。
- 实验代码和日志在 `/tmp/libreshot-memory-analysis/`，其中 `Probe.swift` 和 `build.py` 可重跑；`probe image/png/bothboard/pngboard/long` 分别选择路径。`ocr-baseline`、`ocr-pooled` 是 OCR 对照程序。临时文件可能被系统清理。

## 1. 剪贴板：优先优化重复写入

位置：`LibreShot/LibreShot/CaptureService.swift:157`。

现有路径先编码 PNG，再解码为 NSImage 生成 TIFF，随后再次解码 PNG 并调用 `writeObjects`。这包含重复图片表示和写入。2400×1400 的单份 RGBA 像素约 12.8 MiB，多份解码缓冲足以放大占用。

第一轮实验（MiB，表内“操作中”是采样点，不是连续采样所得真实峰值）：

| 路径 | 首次操作中 | 5 次操作后各等 1 秒的范围 |
| --- | ---: | ---: |
| 当前完整复制路径 | 121.4 | 70.1–118.0 |
| PNG + TIFF，去掉末尾重复 writeObjects | 93.8 | 42.6–66.6 |
| 仅 PNG 写入命名剪贴板 | 65.4 | 12.1–15.7 |
| 仅 PNG 编码，不写剪贴板 | 65.2 | 11.1–14.0 |

重复执行当前路径得到 68.7–104.3 MiB 的操作后范围。清空**测试专用**剪贴板并再等待 5 秒后回到约 9.3 MiB，说明这一实验中的高占用并非全部是永久泄漏。清空剪贴板不是产品优化方案，用户仍须能粘贴截图。

为排除仅是短暂峰值，补测连续 5 次后**保留剪贴板内容、不清缓存**的闲置状态：

| 路径 | 再闲置 5 秒 | 再闲置累计 15 秒 |
| --- | ---: | ---: |
| 当前完整复制路径 | 76.4 MiB | 48.2 MiB |
| PNG + TIFF，去掉末尾重复 writeObjects | 54.8 MiB | 23.0 MiB |
| 仅 PNG 写入 | 13.9 MiB | 10.3 MiB |

保留 PNG/TIFF 的变体在本轮 15 秒采样时比原路径低约 25.2 MiB，支持优先优化该处。它是一次固定尺寸的隔离对照，不能推导所有图片尺寸、机器和完整应用都固定节省 25 MiB，也不能用 15 秒采样证明永远不会再变化。后续 `CIContext.clearCaches()` 在这轮各路径都基本没有改变读数，进一步排除了将这部分差异直接归因于 CI 缓存的解释。

建议先去掉重复 `writeObjects`，保留 PNG/TIFF；后续评估按需提供 TIFF，避免无论消费者是否需要都提前生成。仅 PNG 的读数不能直接作为推荐实现，需要验证 Finder、预览、浏览器、聊天应用和文档编辑器的实际粘贴，尤其透明圆角与 Retina 尺寸。延迟提供数据还需要验证应用退出后剪贴板仍可用。

## 2. OCR：大幅上涨在翻译之前已经发生

位置：`LibreShot/LibreShot/Core/OCR/OCRService.swift:24`。

当前使用 Vision accurate 识别、中英文语言设置和语言校正。1600×900 测试图每次识别出 1335 字符，不执行翻译：

- 第一轮 3 次识别后的内存分别为 86.7、71.9、87.6 MiB。
- 独立复测为 84.3、92.8、90.3 MiB，再等 5 秒为 64.3 MiB。
- 唯一修改为在请求构造和执行周围加 autoreleasepool 的临时版本为 89.9、94.4、88.6 MiB，再等 5 秒为 82.1 MiB；没有证明它能稳定降低占用。

因此不能把截图翻译后的 100 多 MB 全部归因于翻译，也不能宣称多加 autoreleasepool 就能解决。现有程序没有长期保存 VNRequest/VNImageRequestHandler 的成员属性；上述实验能把上涨定位到 OCR 路径，但尚未逐一归因到 Vision 内部模型、缓存和分配器。

建议先保留识别准确率，评估超大选区分块处理来约束峰值。如产品要求 OCR 完成后主进程回到接近冷启动水平，可进一步原型验证按需启动、完成后退出的 OCR helper/XPC 服务。它增加进程通信、启动延迟与打包维护成本，而且不保证降低识别时所有进程的总峰值，不宜作为第一步。把识别移到后台线程可改善响应性，本身不等于释放模型内存。

## 3. 长截图：保留全部完整帧导致额外增长

位置：`LibreShot/LibreShot/CaptureService.swift:651`。

`segments` 为每个新增片段保存 `sourceImage`，但匹配仅需要最新一帧。同时 `CGImage.cropping(to:)` 的结果还会引用原图：本机 SDK 的 `CoreGraphics.framework/Headers/CGImage.h` 明确说明裁剪结果 retains a reference to the original image。只删除 `sourceImage` 字段不够。

使用现有测试的行模式生成 1400×800 彩色帧，每帧向下 72 像素，共 13 帧全部成功接受：

- 11 帧、输出高度 1520 时：62.4 MiB。
- 最终 1400×1664，生成结果时：72.2 MiB。
- 最终图片单份 RGBA 像素仅约 8.9 MiB；这个数不是整个处理流程应达到的总内存。
- 释放 stitcher 和结果后：14.0 MiB。

建议只保留最新完整帧用于匹配，历史片段绘制到独立像素缓冲，解除裁剪图对完整帧的引用；固定底栏也须同样处理。更长内容可再考虑分块存储和输出。该项主要降低长截图过程的峰值，不能据此解释普通截图后的全部闲置内存。实现后必须继续通过已有拼接像素对照测试，防止重复行、丢行、方向和颜色变化。

## 4. 次要项与未证实项

- CaptureService 构造会立即创建 CIContext，但隔离测试仅由约 6 MiB 增到约 7.4 MiB；它不是本轮普通图片实验的主要来源。按需创建、复用与空闲清缓存需要针对实际捕获/滤镜路径测量；清缓存后的下降还可能混有异步回收，不能直接宣称都是 CI 缓存。
- OverlayViewModel 每次接收截图会构造最长边 1200 的 previewBitmap，主要用于马赛克。可以考虑首次使用马赛克时再构造；这属于几 MiB 级的优化，且 reset 已清理此图，收益主要发生在编辑过程中。
- OCRResultWindowController 关闭时清理 contentView，翻译模型 cancel 会将 configuration 置空。源码没有持久保存 TranslationSession。这不构成所有窗口无泄漏的证明。
- 当前安装版 `leaks` 仅报告约 10.8 KiB，但该进程不可调试，报告受限制，不能据此证明无泄漏，也不足以解释几十 MiB 的占用。
- 独立翻译探针返回 `languageNotInstalled`，没有获得可比的翻译内存数值；未自动下载语言包。因此本报告不量化翻译单独增加多少内存。

## 执行顺序

1. 普通截图：消除重复剪贴板图片写入，验证粘贴兼容性和保留剪贴板时的稳定内存。
2. 长截图：解除历史片段对完整帧的保留，检查像素一致性和长时间滚动峰值。
3. 在以上完成后重测完整应用冷启动、取消选区、复制、关闭编辑器、OCR、关闭 OCR 窗口后的 1/5/15/60 秒内存，重复 20 次区分稳定平台与持续增长。
4. 只有 OCR 后的常驻目标仍不满足时，再评估独立进程方案。当前证据不支持承诺完整应用使用所有功能后始终回到 20 MB。

## 已实施与回归（2026-09-15）

生产代码已移除剪贴板末尾重复的 NSImage 写入，保留立即提供的 PNG/TIFF，避免依赖写入进程持续存活。长截图仅保存最新原始帧作为匹配基线，历史片段与底栏绘制成独立 sRGB 像素缓冲，与原有最终渲染使用相同输出格式。全部片段成功准备后才更新拼接状态，避免分配失败破坏已接受内容。OCR、翻译、捕获分辨率及重叠匹配算法没有改动。

同一隔离探针重新编译生产代码后的测量：

| 场景 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 2400×1400 连续复制 5 次，保留剪贴板再闲置 15 秒 | 48.2 MiB | 23.6 MiB |
| 1400×800 长截图 11 帧，输出高 1520 | 62.4 MiB | 21.8 MiB |
| 13 帧长截图生成 1400×1664 结果的采样点 | 72.2 MiB | 29.8 MiB |

新回归在修改前捕获到两个问题：每次复制产生两个图片条目；历史帧的 CGDataProvider 像素存储没有释放。修改后，PNG/TIFF 仍逐像素一致并保留圆角透明度及 Retina 逻辑尺寸，历史帧存储释放而最新匹配帧仍保留，最终图片逐像素一致。使用用户提供的图文混合图片重新拼接也通过像素对照。

最终补充检查也通过：sRGB 和 Display P3 彩色帧拼接与原文档逐像素一致；写入进程退出后，独立读取进程通过 AppKit 读出一个图片条目，PNG/TIFF 数据、透明角及 Retina 尺寸完整。

`tests/run-toolbar-checks.sh` 的 15 组检查通过，包含真实 Vision 中英文 OCR、已安装模型的英译中、自动保存失败保留剪贴板、标注和快捷键。正常签名的 Release `xcodebuild` 成功。以上不能代替所有第三方应用、各 macOS 版本的实际粘贴及真实网页滚动测试，也不代表完整应用必然稳定在上述隔离进程数值。
