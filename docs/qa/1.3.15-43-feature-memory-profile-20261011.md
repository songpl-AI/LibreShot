# build 43 OCR、翻译阶段读数与完整应用使用后内存验证

日期：2026-10-11。本页区分独立诊断探针与最终安装副本的真实使用后观察。本轮没有替换安装包，也没有修改生产代码。MiB 按 1,048,576 字节计算；不同进程的读数分别记录，不能把不同时间的进程最大值相加。

**当前实机结论：用户确认 OCR、图片翻译成功并关闭 LibreShot 的编辑、OCR、设置窗口后，同一 build 43 主进程在 90 秒观察内保持 76.84–77.28 MiB footprint。关闭后仍有一个图片翻译 model，其引用树通向系统翻译回调及 Task/XPC 根，并保留一个 28.33 MiB Data allocation 的图像业务引用链。这给出了具体的生命周期排查方向，尚不构成唯一持有者、完整泄漏根因或优化收益证明。**

后续已据此开展[图片翻译生命周期源码修复与回归](image-translation-cleanup-20261011.md)，包括会话结束撤像素所有权及异步迟到保护。后续源码变化不属于本页实机 build 43；本页全部测量仍描述原安装副本，修复收益待新候选同条件实测。

## 指标与证据边界

- `FeatureMemoryProfile`、`OCRResidencyProfile` 使用 `task_vm_info.phys_footprint`，在指定阶段完成后取单点读数。下表的阶段最大读数不是操作中持续采样峰值，可能遗漏瞬时大分配。
- 完整应用使用后观察使用外部 `libproc.proc_pid_rusage(RUSAGE_INFO_V4)`，每 0.25 秒记录当前 footprint、RSS 及进程生命周期最大 footprint。RSS 不等于 footprint；生命周期最大值也不等于某项功能的峰值。
- 本次采样启动前，用户已经完成普通截图、OCR、图片翻译操作。缺少这轮的操作前基线、各阶段起止及精确关窗时间，不能还原各功能的峰值，不能把后置采样时刻标为关窗后第 1/5/15/60 秒。
- 系统 `translationd` 和 `TranslationAPISupportExtension` 独立列出；它们是系统服务，现有数据没有 LibreShot 独占归属量。

4. 多个 image owner 引用同一个 `CGImage` 不等于多份像素。原图、译图、renderer 或系统缓存各自占用多少，需要 allocation/retain graph 证据。

## 关闭后的对象与引用链

90 秒采样后的 [heap 类型/尺寸清单](../../dist/feature-memory-runtime-20261011/after-close-01/heap-sizes-no-content.txt)显示一个 `OverlayViewModel`、一个 `ImageTranslationModel`，同时有 `TranslationSessionViewModel` 与 `TranslationSession`。没有明确的 editor/overlay/image-translation controller 类型实例。该清单只提供对象数量与 allocation 大小，没有读取截图像素或 OCR/译文。

[ImageTranslationModel 反向引用树](../../dist/feature-memory-runtime-20261011/after-close-01/translation-model-retain-tree-no-content.txt)给出的两个 root 路径共享下列前缀：

```text
ImageTranslationModel
  ← closure context（unknown layout）
  ← closure context（unknown layout）
  ← LanguageSupportHostModel._completion.context（__strong）
      ← Task stack → Swift Task Owned root
      ← NSXPCConnection exported table → XPC/block → Kernel Pointers root
```

这证明该次快照中 model 仍可由系统翻译 completion/Task/XPC 根到达，不能简单解释为只有空闲 allocator 页保留。[OverlayViewModel 的独立引用树](../../dist/feature-memory-runtime-20261011/after-close-01/overlay-model-retain-tree-no-content.txt)指向相同的两个 closure 地址和同一个 `LanguageSupportHostModel._completion.context`，与 inline 视图同时持有两个 model 的源码结构吻合。但它不证明两个未知布局 closure 对应源码中的哪一个闭包，不证明任务一定仍在执行，也不证明连接永久不释放或一定由系统框架缺陷导致。需要合成素材的生命周期复现及关闭前后对照。

源码中，[inline view](../../LibreShot/LibreShot/Core/OCR/ImageTranslationWindowController.swift) 的 `.task`、`.translationTask` 和回调直接访问 `model`/`viewModel`；`ImageTranslationModel.original` 是不可置空的 `let NSImage`，`cancel()` 会清除译图、configuration 和请求状态，但保留原图。即使框架只保留一个旧回调，也可能延长原图生命周期。[OverlayViewModel](../../LibreShot/Features/Overlay/OverlayViewModel.swift) 中的原图由全屏预览 crop 得到，crop 还可能共享原始 backing。

### 大 Data allocation 的业务持有路径

[heap 大对象地址清单](../../dist/feature-memory-runtime-20261011/after-close-01/large-buffer-addresses-no-content.txt)确认 `0x6e9400000` 是一个 **29,704,192 bytes（28.33 MiB）** 的 `__DataStorage._bytes` 活跃 allocation。[该地址的反向引用树](../../dist/feature-memory-runtime-20261011/after-close-01/large-buffer-retain-tree-no-content.txt)包含以下字段明确的业务路径：

```text
Data allocation 0x6e9400000
  ← CGDataProvider ← CGImage ← CGImage
  ← NSCGImageSnapshotRep ← NSImage
  ← ImageTranslationModel.original
  ← closure ← LanguageSupportHostModel._completion
  ← Task / XPC roots
```

因此该大 allocation 与残留图片翻译 model 的原图链已关联；无需读取用户图像内容。[原图 NSImage 的独立引用树](../../dist/feature-memory-runtime-20261011/after-close-01/original-image-retain-tree-no-content.txt)同时列出 `ImageTranslationModel.original` 和 `CA::CG::AccelRenderer` 两条路径。完整大 buffer 树还列有 `CA::Render::image_cache`、malloc reclaim buffer、字体/metadata 等其他根；其中保守指针扫描路径不能逐一当成真实强 owner。现有图不能证明 `original` 是唯一持有者，也不能保证仅释放 model 就立即释放 allocation。

采样后、heap 前的 [vmmap](../../dist/feature-memory-runtime-20261011/after-close-01/vmmap-full-before-heap.txt)从同地址 `0x6e9400000` 开始列约 22.7 MiB 全部 swapped 的区域，后接 5,808 KiB（约 5.67 MiB）零 resident/dirty/swapped 的区域。两段合计约 28.33 MiB，对应同一 heap allocation 跨 VM region，不能误写成两个活跃大对象。该 allocation 的已归属 dirty+swap 量约 22.7 MiB，当前 resident 为 0；allocation 大小、footprint 归属量和当前驻留 RAM 是不同指标。因此不承诺释放 model 后等额下降 28.33 MiB，实际优化收益需同一 fixture 的前后测量。

[leaks 检查](../../dist/feature-memory-runtime-20261011/after-close-01/leaks-no-content.txt)报告 330 个、合计 15,616 bytes 的 leak/cycle，主要在 XPC/辅助功能对象。这个小量不足以解释几十 MiB 的平台；可由 Task/XPC 根到达但已不需要的 model/图像也不一定被 `leaks` 标为 unreachable leak。因此不能用该报告宣布不存在业务生命周期问题。

14:36:09（UTC+8）的 [扫描后身份快照](../../dist/feature-memory-runtime-20261011/after-close-01/post-scans-spot-check.json)再次确认同一 PID、启动标识及主程序 SHA，窗口查询返回 0，footprint 77.25 MiB、RSS 99.23 MiB。该点在 heap/leaks/引用树扫描之后，只作仍存活现场与窗口状态的核对，不追加为自然待机回落曲线，也不是功能峰值。

## 已完成的合成生命周期验证

[Synthetic lifecycle 报告](../../dist/feature-memory-runtime-20261011/synthetic-lifecycle/REPORT.md)及 [results.jsonl](../../dist/feature-memory-runtime-20261011/synthetic-lifecycle/results.jsonl)来自独立诊断进程 PID 65231，通过现有编译入口使用生产 model/renderer 源码与临时探针。没有真实 OCR、真实翻译或 UI 窗口，没有读取用户截图，也没有修改生产源码、安装副本、权限或设置。已运行的 LibreShot 没有被停止或重启。

四类检查全部完成：

| 验证 | 实际结果 | 结论边界 |
| --- | --- | --- |
| mock OCR/翻译完成→真实 renderer→cancel→退出作用域 | `cancel()` 后译图 NSImage 弱引用为 nil，原图/model 仍活；作用域退出并等待调度约 30 ms 后 model、原图、译图弱引用均为 nil，原始 provider sentinel 释放恰好 1 次 | 该 headless 完成路径未出现 model 永久自环；cancel 会保留供重试的原图 |
| mock OCR 悬挂在可取消 sleep→cancel→作用域退出 | recognition task 收到取消，结束后 model/原图弱引用为 nil，provider sentinel 释放 1 次 | 当前 model 的 OCR 取消能传播到该 mock；不替代生产 worker 实机取消验收 |
| mock 翻译悬挂在故意不响应取消的 continuation→cancel/撤外部引用→恢复 | 悬挂期间 model、原图、provider 仍活；恢复 continuation 后过期结果被丢弃，方法返回并撤 task 引用后全部释放 | 异步调用未结束可以保留 model/原图；该 mock 不证明系统 `TranslationSession` 不响应取消或真实任务的结束时机 |
| 小 crop→撤原始全图→撤 crop | 320×160 crop 的 provider wrapper 身份不同，但撤全图后原始 sentinel 仍活，撤 crop 才释放 1 次 | 该 crop 共享原始 backing；不同 provider 身份或较小 exposed data 长度不能证明像素已分离 |

合成源图固定为 **2400×1600 像素、1200×800 point、sRGB、8 bpc/32 bpp**，原始 stride 9664、allocation 15,462,400 bytes（14.746 MiB），renderer 输出 stride 9600。320×160 crop 仍使用原始 stride 9664，暴露 data 长度为 1,537,856 bytes，但实际保留的是原始 allocation 的 provider 链。

探针使用 provider release callback/sentinel 和 Swift model/NSImage 弱引用；最初试图给 CoreFoundation wrapper 建弱引用时失败，已拒绝的日志保留，不计为通过。此轮没有 SwiftUI hosting、`.translationTask`、系统 TranslationSession 或 AppKit 窗口，尚未复现实机系统 completion 的关闭后生命周期。纯白合成位图还可能触发 CoreGraphics 优化，探针 footprint 单点只作上下文，不作实机峰值、分配栈归因或释放后物理页立即归还的证据。

## 当前判断与下一步

1. 独立文本翻译探针增量较小，生产 helper OCR 父探针能回落；这些证据不能替代真实完整应用的阶段峰值。诊断 worker 的 95–97 MiB 不作为 build 43 生产 helper 的内存结论。
2. 完整应用成功使用 OCR/图片翻译并关窗后约 77 MiB footprint 暂留；引用树已指出残留图片翻译 model 经系统 completion 被持有，并通过 `original` 到达大 Data 图像 backing。优先验证这条生命周期，完整 roots 的确切 owner 及关闭后的释放策略仍需实验。
3. 合成 headless 生命周期已验证：没有完成路径的永久自环；悬挂异步调用会保留原图；crop 会保留全图 backing。接下来用合成素材 hosting 对照真实 `.translationTask` 的配置置 nil、拆 host、回调弱捕获和 owner 终止会话，核验 weak model/NSImage 与 provider release，而不是继续让用户反复操作截图。
4. 最小修复候选是区分“取消后可重试”与“永久结束会话”：保留前者的原图，在 owner `clearImageTranslation`/`reset` 或真正窗口关闭时幂等终止请求并释放 `original` 等像素状态；`.translationTask` 回调只捕获必要对象并评估弱捕获。不能一律把 `.onDisappear` 改成永久清空，因为 overlay 的 `accessoriesAbove` 两个条件布局分支可能拆除/重建 inline 视图，这会破坏仍在使用的翻译或重试。需先验证布局移动、相同语言重试、撤译图、真正关闭及过期结果门禁。本轮只记录候选，没有实施生产修复。
5. 下一轮功能操作前先启动采样，各功能独立区间，记录开始、完成、关窗时刻，分列主进程、准确路径及父 PID 的生产 helper、系统服务；再得到 sampled maximum 和回落数据。避免为补日志重建已验收包，避免重复要求用户执行不稳定桌面自动化。
6. 长截图此前同包另一 PID 观测到约 208.7 MiB，随后约 0.5 秒为 87.8 MiB、约 1 秒为 47.2 MiB、约 96 秒为 39.7 MiB，详见 [long-memory-summary.json](../../dist/long-capture-refactor-20261011/runtime/long-memory-summary.json)。该峰值与保存阶段相邻，具体是最终位图、图形 surface、编辑器交接或 PNG 编码，仍需 Allocations/VM Tracker/分配栈确认；不能归因于本次 OCR/翻译，亦不能把它当本 PID 的操作前基线。
